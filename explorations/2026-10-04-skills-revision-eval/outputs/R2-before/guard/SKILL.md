# Skill: Entropy Guard

A post-work micro-ritual for this project. Run this when you finish a meaningful piece of work, before you consider it done.

> **Scope**: what changed in *this session* — not a full project audit. This takes 2–5 minutes. If you find yourself doing a comprehensive review of all project docs, you've scope-crept. Stay focused on the delta.

> **Generated by**: running the front-door [entropy assessment](../../entropy-assessment/) against this project (2026-03-19), then refined by running the specialized [docs-first planning assessment](../../docs-first-planning-assessment/) against it (2026-04-07, 2026-10-04). This guard is both the project's own quality mechanism and a reference example of the docs-first planning output.

> **Why this is one combined guard**: this repo's main entropy risks span documentation, the exported skills, and workflow/practice drift, but they share one stable, low-burden trigger: end of a meaningful work session / before commit. Keeping them together is the lower-ceremony design.

> **Guard metadata**:
> - Generated: 2026-03-19, via entropy-assessment v0.4.0
> - Last evaluated: 2026-10-04, via entropy-assessment v0.6.0 routed to docs-first-planning-assessment v0.1.0 (snapshot 447da9a)
> - System snapshot: documentation-as-system repo with 4 exportable skills (two of which generate session-end guards), 2 local skills, AI-agent contributors from more than one vendor, TODO-driven session workflow, a historical `explorations/` folder, and no application code, tests, API, or CI
> - Integration: standing instruction in AGENTS.md, a non-blocking local pre-commit reminder via `.githooks/pre-commit`, and `CURRENT_STATE.md` read at session start

## When to Run

- You've completed a task and are about to commit
- You've resolved a non-trivial problem and the solution has implications beyond the immediate fix
- A session is ending and you want to leave the project in a clean state

## When NOT to Run

- After trivial changes (typo fixes, minor formatting) — use judgement
- As a replacement for a full re-evaluation — re-run [`skills/entropy-assessment/SKILL.md`](../../entropy-assessment/SKILL.md) against this repo for that (the evaluator role in INTENT.md)
- More than once per logical piece of work

## Checklist

Work through each question in the context of what you just did. Most answers will be "no, nothing to do" — that's fine and expected.

### 1. Decisions
- Did you choose between approaches, patterns, or structures?
- Did you decide *against* something?
- Did you discover a constraint that will shape future choices?
- Did you establish a convention (naming, file structure, process)?

If yes to any: does it appear in DECISIONS.md? Add it if not. One entry, concise: date, context, decision, impact.

- Does the new decision replace or narrow an earlier entry? If so, add a marker line under the earlier entry: `*Superseded by "<title>" (<date>).*` or `*Partially superseded by "<title>" (<date>): <which part no longer holds>.*`

> *Rationale*: This project evolves through conversation sessions. Decisions made in one session are invisible to the next unless captured. On 2026-10-04, 5 of 17 entries described skill structure that a later decision had replaced (an entropy-assessment Phase 2, domain appendices) with no marker, so a fresh agent could reasonably try to restore them. Entries were undated, leaving file order as the only supersession signal.

### 2. Learnings
- Did you discover a non-obvious behaviour, gotcha, or pattern?
- Did something fail in an unexpected way and you found out why?
- Did you validate (or invalidate) an assumption about how something works?
- Did a concept from INTENT.md prove useful (or inadequate) when applied to a real case?

If yes to any: does it appear in LEARNINGS.md? Add it if not. Insight + what validated it + implication.

- Was it validated by use (a run against a real repo, a review, a failure)? A conclusion validated only by conversation belongs in PHILOSOPHY.md or the sibling `entropy-immune-system` repo, per the "LEARNINGS.md stays tactical" decision.
- Did this session remove or replace something an existing learning names in its *Validated by* or *Implication* line? Annotate that learning.

> *Rationale*: Same session-boundary problem as decisions. This project generates methodology insights — learnings about how guards work, what entropy vectors matter most, what the generators get right or wrong. These are easy to lose, and easy to dilute with theory that has not been tested on a real system.

### 3. Skill Role and Intent Alignment
- Did you create, remove, rename, or change the role of a skill?
  - Does `skills/entropy-assessment/SKILL.md` Step 3 still route each system shape to the skill that now serves it?
  - Does INTENT.md "The guard lifecycle: four distinct tools" still name which skill carries each role?
  - Do the other skills that name it still describe its role correctly? (`guards-integrator` "When to Run" and "What This Is Not"; `docs-first-planning-assessment` "When NOT to Run")
  - Does an exportable skill end with the upstream feedback check the other exportable skills carry?
  - Does its frontmatter `name` equal its directory name?
- Did you rewrite, move, or delete part of a skill?
  - Search DECISIONS.md and LEARNINGS.md for the skill's name. Does each behaviour they require of it still exist somewhere? If you dropped one on purpose, mark the entry superseded (check 1). If not, restore it.
- Does the skill still reflect the principles in [INTENT.md](../../../INTENT.md)?
  - Does it preserve the "low burden" design requirement?
  - Does it scope to the delta, not a full audit?
  - Does it map entropy vectors to the appropriate enforcement depth?
  - Does it address inter-domain drift where relevant?

If misaligned: update the skill, or if INTENT.md itself needs revision, update it with a dated note explaining what prompted the change.

> *Rationale*: The skills are this project's product, and INTENT.md encodes its principles. On 2026-10-04 two misses of exactly this kind were found: `session-coherence-skill-generator` had been added with no route from the front door and no place in the INTENT.md lifecycle, and the "verify bootstrap actions against the current artifact" requirement recorded in DECISIONS.md had silently dropped out of `docs-first-planning-assessment` during its rewrite.

### 4. Workflow / Practice Alignment
- Did you change how contributors are supposed to work in this repo?
- Did you change when guards run, how TODO.md or CURRENT_STATE.md is used, or how upstream feedback gets captured?
- If an agent started from `AGENTS.md` and `CURRENT_STATE.md` alone, would it follow the workflow you actually used in this session?
- Do `AGENTS.md`, `README.md`, `TODO.md`, `.githooks/pre-commit`, and the local skills still agree about the live iteration loop?

If not: update the workflow docs now. In this repo, practice drift is as damaging as documentation drift because the workflow is part of the product.

> *Rationale*: This project does not just describe guards; it demonstrates them in use. If contributor instructions, TODO discipline, or feedback loops drift from reality, the repo stops being a trustworthy reference implementation.

### 5. Canonical Ownership and Internal Consistency
- If a concept changed, does it still have one canonical home? The usual homes here:
  - purpose, entropy model, guard lifecycle, enforcement depth → INTENT.md
  - which skill serves which repo shape → `skills/entropy-assessment/SKILL.md` Step 3
  - how to work in this repo → AGENTS.md
  - settled choices → DECISIONS.md
  - active work → TODO.md; session-start orientation → CURRENT_STATE.md
  - theory and philosophy → PHILOSOPHY.md fragments; the sibling `entropy-immune-system` repo for the larger inquiry
- Do nearby docs carry a link or a local implication, rather than a second full explanation?
- Did you change something that another doc also describes? If so, update both, or reduce one to a link.

If inconsistent: fix it now. Internal consistency drift is this project's primary entropy vector.

> *Rationale*: Nearly every doc here cross-references others, so any structural change creates a wave of stale references. Two docs that are each independently complete about one concept drift apart even when every edit is careful.

### 6. Key Files / Architecture
- Were any files added, removed, or renamed?
- Was a significant responsibility moved from one file to another?
- Did the skill directory structure change?

If yes: is this reflected in all three listings — AGENTS.md "Quick Links", AGENTS.md "Key Files", and README.md "What's here" tables? Historical material (`explorations/`) is listed as historical, not as live guidance.

> *Rationale*: Structural changes propagate — a renamed file needs updating in every doc that references it.

### 7. Cross-References and Supersession
- Did you rename, move, or delete anything that docs link to?
- Are there references to file paths, section names, line numbers, or document counts that are now wrong?
- Before restoring a deleted file or section, fixing a broken reference by recreation, or reviving a concept: was it intentionally superseded in DECISIONS.md, CURRENT_STATE.md, or another current-shape doc? `explorations/`, superseded DECISIONS.md entries, and theory in PHILOSOPHY.md are historical context, not current guidance.

If yes: fix the broken references. Run a quick grep for the old name to catch all occurrences.

> *Rationale*: Link rot is a fast-decaying, cheap-to-fix entropy vector — but only if caught within one iteration. Left for multiple sessions, it becomes archaeology. Relative-link resolution is the first candidate to move into a non-blocking script (semi-embedded enforcement).

### 8. Stale Placeholders
- Are there any `[Add X here]` or `[TBD]` sections that you can now fill in? (`[empty]` under TODO.md "Doing Now" is deliberate.)
- Are there empty sections in docs that the work you just did actually answers?

If yes: fill them in or remove them. Stale scaffolding is worse than no scaffolding.

> *Rationale*: Placeholders are an honest admission of incompleteness. They become dishonest when the information exists but the placeholder persists.

### 9. Guard-Induced Entropy
- Did you add or propose automation (a script, a hook line, a CI step, a template check)?
- Is the invariant durable — link resolution, required files, frontmatter `name` matching the directory, skill directories listed in README and AGENTS?
- If it mostly encodes current wording, headings, path names, or transitional terms, keep it in this narrative guard for now.

> *Rationale*: A check that churns faster than the thing it checks becomes a new entropy surface and teaches people to ignore the guard.

### 10. Current State: TODO.md and CURRENT_STATE.md
- Is "Doing Now" cleared?
- Are any completed items still marked as active?
- Did this work surface anything that should be in "Next Up" or "Backlog"?
- If CURRENT_STATE.md exists: did this session change the stage, the docs to trust first, the settled list, the active fronts, the open questions, or the nearby superseded material? Update it, and keep it to one screen.
- If this session ran an external validation (an assessment of another repo), is its result recorded where the repo records validation results?

Update TODO.md and CURRENT_STATE.md to reflect the current state before committing.

> *Rationale*: TODO.md is the project's live state; CURRENT_STATE.md is what the next fresh session reads first. Stale state in either is state entropy — the project can't accurately describe its own condition, and the next session starts from the wrong truth.

## Output

After working through the checklist, note briefly what was updated (or "entropy check clean"). Include this in your commit message if anything changed.

If the main issue was workflow/practice drift, or a skill whose role or decided behaviour had drifted, rather than a missing doc update, say that explicitly so future contributors can tell which part of the system needed attention.

## What This Is Not

- A full re-evaluation — re-run `skills/entropy-assessment/SKILL.md` against this repo whenever an exportable skill is added, removed, or changes role
- A reason to delay committing — if the check surfaces a large gap, file it in TODO.md and fix it in a follow-up commit rather than expanding scope mid-task
- A place to track one-time cleanup — bootstrap and cleanup items live in TODO.md, not in this file
- A static artifact — this guard should itself be re-evaluated periodically by running the generator against the project again
